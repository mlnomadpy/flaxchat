# Harness review: quality, cost and research priorities — 2026-09-21

The highest-return work is to unify the validated training path, correct optimizer and token accounting, and measure quality per dollar before introducing more architectural complexity. The recent physical TPU campaign is valuable evidence, but it does not establish that every pretraining, SFT and RL entry point shares its guarantees.

This review inspected model/attention, optimizers, both pretraining paths, packing and token pools, checkpointing, SFT/RL, evaluation, launch adapters, GCP setup/cleanup, configuration, tests and benchmark protocols. It includes targeted CPU reproductions and primary literature checked on September 21, 2026. It is not an exhaustive proof or a new TPU performance campaign. No TPU was provisioned, production implementation changed, or GitHub issue posted for this review. Kaggle remains excluded.

The reviewed Python source digest is the same `e7e303fc66515bb3def748bf6022ace6a936a34e7317ebf2bc85c7e476d16c37` used in the recent physical campaign. Existing evidence: 458 TPU unit tests passed, four intentional skips had complementary CPU coverage, nine multi-host acceptance stages passed, and two FSDP scale smokes passed. Those results cover the selected configurations; the findings below identify missing contracts and combinations.

**What should remain the foundation**

Keep explicit pre-backend distributed initialization, canonical prepared-token ordering, global checkpoint cursors, strict checkpoint integrity, source/environment identity, finite-gradient checks, forced-kill recovery, physical-host assertions and bounded cloud teardown. Preserve the pinned evaluation datasets, prompt manifests and confidence intervals. Do not replace these with a new framework merely to acquire one optimization.

**Findings to address before a long training run**

Priority P1 means fix before spending on the affected path. P2 means a meaningful correctness, performance or maintenance gap. “Reproduced” means a local executable probe; “static” means a concrete code-path finding, not a newly observed TPU failure.

**Integrations with the best near-term return**

| Order | Integration | Why it is worth doing | Effort estimate / acceptance |
|---|---|---|---|
| 1 | One resolved training contract and common training/checkpoint core | Makes correctness fixes, optimizers, accumulation and infrastructure improvements apply to the actual production path. | Medium–large; actual global tokens and resumed model/optimizer/cursor must match the baseline. |
| 2 | Pinned data recipe + reference evaluation adapter | Training quality depends on which tokens are learned, and trustworthy evaluation is needed to select every later change. | Medium; document-disjoint and duplicate-audited holdouts, stable domain mixture, exact task parity and recorded protocol. |
| 3 | Persistent compilation cache, lean locked worker image, staged data | Avoids rebuilding environment, downloading test-only packages and compiling identical programs after Spot restarts. All ranks need access to cache entries. | Small–medium; fresh/warm/restarted job timings and exact source/environment identity. [JAX cache documentation](https://docs.jax.dev/en/latest/501/compilation-cache.html). |
| 4 | ML Goodput Measurement + cost ledger + cloud-side teardown | Distinguishes useful committed training from setup, evaluation, checkpoint and recovery overhead. | Medium; include every attempt and chargeable interval; inject controller loss and confirm owned-node deletion. [Google goodput guidance](https://docs.cloud.google.com/tpu/docs/goodput). |
| 5 | Sharded async checkpoints with adaptive cadence | Current validation used frequent synchronous saves for evidence; production should minimize exposed save time and replay cost. Async alone does not fix the synchronous full-state hashing path. | Medium–large; kill during write and during finalization, retain the prior committed checkpoint, check bounded memory. [Orbax async checkpointing](https://orbax.readthedocs.io/en/stable/guides/checkpoint/async_checkpointing.html). |
| 6 | Explicit BF16 compute, selective remat and batch tuning | Establishes predictable dtype/memory behavior, then trades recomputation against a larger useful batch. | Medium; at least 100 measured post-warmup updates plus quality and recovery checks. |
| 7 | Chunked loss and shard-local Splash | Removes potentially large vocabulary/attention memory costs without changing the intended objective. | Medium–large; exact FP32 oracle, BF16 tolerance, masked/GQA/sliding-window cases, FSDP=1/4/8. |
| 8 | Grain behind the data adapter, if custom loader complexity grows | Reuses checkpointable iteration, multiprocessing/prefetch and packing implementations; not a reason to discard the already working canonical token pool. | Medium; compare next-token IDs and consumed cursor after arbitrary stops. [Google Grain packing implementation](https://github.com/google/grain/blob/main/grain/_src/python/dataset/transformations/packing_concat_then_split.py). |

Effort labels are relative engineering judgments, not delivery-time promises. None of these entries has a measured percentage saving in this harness yet.

For checkpoint cadence, measure durable save latency and restart/replay loss, then search a few intervals. A fixed “every four steps” is appropriate for recovery tests, not automatically for production. Maintain a durable GCS checkpoint; local-only recovery is not sufficient for an entire Spot slice disappearing.

Keep a single-host slice for iteration when the model fits. Use multiple hosts when memory or measured elapsed time justifies the extra coordination, not because more chips are inherently cheaper. GKE/XPK becomes attractive for recurring large workloads; I would not spend the present budget migrating all orchestration to Kubernetes first. Google currently documents manually approved v4 quota in us-central2-b, and the previous attempt did not establish access. Do not plan around unverified v4 capacity. [TPU v4 documentation](https://docs.cloud.google.com/tpu/docs/v4).

These recommendations combine recent work with older, well-supported foundations. Paper results are not promised speedups on this code, model size or TPU generation.

I would also defer MoE/expert parallelism, speculative training architectures, Titans-style memory redesigns, broad new RL algorithms and FP4 pretraining. This is a prioritization judgment for the present budget, not a claim that these methods never work. They expand the testing surface before the current dense training path and evaluation contracts are settled.

**Budget and decision rules**

Use cost per *committed useful token* and cost to reach a held-out quality target. A useful estimator is:

`cost per billion tokens = whole-slice USD/hour × 1e9 / (3600 × end-to-end committed tokens/second)`.

Use all-in elapsed time for that rate, including setup, evaluation, checkpointing and replay. Keep device-step throughput as a separate diagnostic. Compare only matching data/tokenizer/architecture/precision/quality criteria, and record valid assistant tokens separately for SFT. The previous four-update scale results are too short to forecast a full training bill.

Treat the $900 as a total ceiling and reconcile actual charges first. A proposed envelope is $50 retained for the previous validation and its billing uncertainty, $100 for fixes plus targeted profiling/recovery validation, $100 for a small number of quality ablations, $550 for the selected training recipe, and $100 for retries/storage/evaluation reserve. These are proposed caps, not authorization for new spending or a bill estimate. No compute was launched during this review.

Measure actual available slices rather than selecting by peak FLOPs. For example, a 50% step speedup does not make a slice economical if its hourly price doubles. Choose the cheapest quality-matched run after accounting for capacity, queue wait, setup, preemption and checkpoint costs. Do not multiply independent paper speedup claims together.

For scratch training, start with a bounded dense-model pilot (roughly 50–150M parameters is a candidate range, not a promised optimum), measure sustained behavior, then choose model size and tokens from the remaining budget. If the goal is a useful assistant rather than studying pretraining, adapting a capable open checkpoint can be a better budget allocation; that requires an explicit compatible import/tokenizer path and its own quality validation. A $900 budget does not justify promising competitive general-purpose quality from scratch.

**Implementation sequence and release gates**

1. Correct R1/R2/R3 and evaluation parity. Add per-group LR/update tests, actual-token accounting, accumulation equivalence and exact recovery for the production entry point. Require a fail-closed optimizer identity and fully resolved effective configuration.
2. Fix BF16 compute policy and large-state initialization/restore. Add HBM/host-memory measurements, chunk integrity tests and corruption/preemption-during-save fault injection. Test both a model that fits replicated and one whose state requires sharding when budget allows.
3. Add compile cache, prefetch, locked lean image and goodput/cost telemetry. Profile one representative workload for at least 100 measured updates after warmup. Choose DP versus FSDP from that evidence.
4. Implement loss-only chunked CE, then shard-local Splash if profiles justify it. Retain exact reference kernels and backend-specific regression tests.
5. Spend the ablation cap on a curated data mixture and corrected AdamW versus Muon first. Select at most one newer experiment: SF-NorMuon or curriculum/model averaging. Use successive screening with full-horizon confirmation, because early optimizer rankings can mislead.
6. Launch the longer pilot only after the exact command/config/image/data manifest is validated. Publish raw results, uncertainty, cost accounting and the remaining unsupported scales. Then address packed SFT and offline preference optimization.

Acceptance should include adversarial configuration combinations, not just more happy-path unit tests: standard/extended GPT × loop/scan; fixed/accumulated batch; DP/FSDP; 1/2 hosts; interrupted writes; different vocabulary masks; source/data mismatch; failure after finite gradients; and controller loss during cleanup. Expand combinations selectively according to what production actually enables.

The existing passing tests remain useful. The new local reproductions show why adding contract tests and validating the precise production recipe should precede the next substantial training spend.
